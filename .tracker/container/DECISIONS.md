# worse::core::container — DECISIONS (ADR)

Locked-in choices for the container library. Confirmed with the user on 2026-06-01.
Change only with a new dated entry below + the user's sign-off.

## User-confirmed (2026-06-01)
| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Benchmark framework | **nanobench** (single-header) | runs inside a gtest `TEST`, no extra link surface; separate optional `wcontainer_bench` target gated by `WORSE_BUILD_BENCH OFF`. |
| D2 | Hash container architecture | **open-addressing Robin Hood** | flat/contiguous, cache-friendly, power-of-two + bitmask. Trade-off: refs/iterators invalidate on rehash/erase — documented contract. |

## Adopted defaults (agent-chosen, game-perf oriented)
| # | Decision | Choice | Why |
|---|---|---|---|
| R1 | `IsTriviallyRelocatable<T>` default | opt-in: `is_trivially_copyable` ⇒ true, else user-declares via `WE_DECLARE_TRIVIALLY_RELOCATABLE` | zero false positives; covers most POD game data. |
| R2 | `Pair` field names | public `first`/`second` | keeps structured bindings; the one STL muscle-memory worth honoring. |
| R3 | Strong-guarantee grow rollback | implement, compiled out when element move is `noexcept` / `-fno-exceptions` | no cost on the common path. |
| R4 | `at()` out-of-range | debug `WE_ASSERT` + abort; release UB (no throw) | matches engine's no-exceptions contract. |
| R5 | `StaticArray` storage | plain `T mData[N]` | constexpr-friendly, std::array-like; needs default-constructible T. |
| R6 | `FixedArray` overflow | hard-cap `WE_ASSERT` (no heap spill) | zero-alloc guarantee is the whole point; heap-spill is a later opt-in param. |
| R7 | `FixedArray` size repr | `usize mSize` (NOT a self-pointer) | a pointer-into-self would dangle after a memcpy relocation; an index relocates cleanly. |
| R8 | Hash probe scheme | Robin Hood + backward-shift delete (no tombstones) | see D2. SwissTable is a Phase 6 upgrade behind the same facade. |
| R9 | Hash slot layout | AoS `Pair` slots first | SoA is a later perf option that complicates iterators. |
| R12 | Algorithm API | iterator-pair, no `<ranges>` | avoid `<ranges>` codegen/compile cost in an engine lib. |
| R13 | `stableSort` | deferred | needs O(n) scratch (allocator dep on the algorithm module). |
| R14 | Debug iterator tripwire | include behind `!NDEBUG` | catches cross-thread/invalidation misuse, zero release cost. |
| R15 | `FlatMap` stored element | `Pair<Key, T>` with a **non-const** key | a contiguous backing `Array` must move/relocate elements on insert/erase, which a `const` key forbids. A const-key proxy facade (boost flat_map) fights relocation; deferred. |
| R16 | Flat-container iterator constness | `FlatSet` iterators const-only (keys immutable); `FlatMap` iterators mutable but **only `.second` may change** | mutating a key silently breaks the sorted invariant — documented contract, not enforced. Change a key via erase+insert. |
| R17 | `PriorityQueue` default order | `Less<>` ⇒ **max-heap** (`top()` is largest), `Greater<>` ⇒ min-heap | matches `std::priority_queue`; heap maintenance routes through the `heap.cppm` algos. |
| R18 | `IntrusiveList` shape | move-only, embedded circular sentinel, **O(1) `size()` counter**, nodes externally owned | size counter stays correct only because ALL mutation goes through the API (no self-unlink); move/swap re-seat boundary links to the new anchor. |

## Phase 4 additions — hash family (2026-06-01)
| # | Decision | Choice | Why |
|---|---|---|---|
| R19 | Default hash algorithm | integer keys: **murmur3 `fmix64`** finalizer; byte ranges: **FNV-1a** (`hashBytes`); multi-field: golden-ratio `hashCombine` | strong avalanche so `hash & mask` spreads sequential integer keys on power-of-two tables; cheap + branch-free. `Hash<T>` primary is declared-undefined so unsupported keys fail `HashFor` and users specialize. |
| R20 | **Float hashing deferred** (user-confirmed) | `Hash<T>` ships integral/enum/pointer/bool/char only; `f32`/`f64` deferred | floats need `-0.0`/NaN canonicalization before a bit hash is sound. Tracked in persistent memory `hash-float-deferred`. |
| R21 | Hash-container lookups | **exact `Key` (non-templated)** find/contains/count/erase (user-confirmed) | transparent/heterogeneous hashing needs a transparent `Hash`+`KeyEqual`; a templated `find<K>` under a non-transparent hash silently misses. Deferred to Phase 6 with string types. Side benefit: non-templated `erase(Key)` sidesteps the erase-overload trap. |
| R22 | Hash slot info type | **`u16` DIB** (displacement-from-ideal-bucket), `0`=empty, occupied=`disp+1` | a degenerate hash (all keys colliding) grows displacement with element count — a `u8` (max 254) corrupts under heavy-collision workloads; `u16` keeps them correct at negligible metadata cost, overflow aborts (no-exceptions). Refines the plan's tentative `u8`. No cached hash in v1. |
| R23 | Hash table tuning | `kMinCapacity = 16`, **max load 7/8 (0.875)** compile-time constant (no runtime setter), power-of-two + bitmask, wrap-around probing, **two allocations** (slots + info), lazy (0 capacity until first insert) | game-perf defaults: fewer early rehashes on populate-then-read; 7/8 balances speed/memory for Robin Hood; single-block slots+info layout is a later cache optimization. |
| R24 | Hash table erase | **backward-shift, no tombstones** (per R8); copy preserves exact RH layout; move steals buffers (noexcept, allocator always-equal) | tombstones degrade open-addressing over time; backward-shift keeps probe runs tight. Engine carries a `checkRobinHoodInvariant()` test hook. |

## Phase 5 additions — node lists (2026-06-01)
Game-perf direction (user-confirmed): design for games, reference **EASTL / Unreal**, do NOT blindly
mimic the STL. `list` + `forward_list` this phase; `fixed_list`/`fixed_slist` (inline zero-heap node
pool) deferred to **P5b**; rb_tree + set/map still deferred.
| # | Decision | Choice | Why |
|---|---|---|---|
| R25 | Node-list Base/Derived split | the destroy-all-nodes loop lives in `ListBase`/`ForwardListBase` **destructor** (value-destroy + free per node), NOT the derived dtor as Array does | a node is inseparably storage + a live value, freed in one step, and both need the allocator the base owns; the derived needs no dtor. Deliberate, documented deviation from `ArrayBase`'s raw-free-in-base / element-destroy-in-derived split (there is no raw-vs-live split per node). |
| R26 | Range-splice count accounting | cross-list range `splice`/`spliceAfter` counts the range with `distance` (O(range)); same-list relinking (sort/merge internals) leaves `mSize` untouched (O(1)) | keeps the O(1) `size()` correct; matches counted lists in EASTL/Unreal and the std cross-container wording. |
| R27 | `remove`/`removeIf`/`unique` return type | return `SizeType` (count removed) | game-useful, avoids a re-count; matches C++20 std::list. |
| R28 | `forward_list` shape | **NOT the std-crippled shape**: minimal single-pointer node + the correct `*After` API (beforeBegin/insertAfter/emplaceAfter/eraseAfter/spliceAfter) **plus O(1) `size()`** and the full algorithm surface. Front-ops only — **no `back`/`pushBack`/tail** | the reason to exist over `List` is the smaller node + minimal object; a size counter is what std dropped on purpose but games want it (R30). A tail pointer would change the storage shape — that's a different (queue) structure. |
| R29 | Node-list trivial relocatability | NOT declared trivially relocatable | `List`'s embedded sentinel is the target of self-referential boundary links — a `memcpy` of the container corrupts the ring; kept consistent for `forward_list`. |
| R30 | O(1) cached `size()` on both | `usize mSize` counter | game-ergonomic (Unreal `GetCount` O(1)); accepted tradeoff is R26. The conscious EASTL/Unreal divergence from `std::forward_list`. |
| R31 | `list::sort` / `forward_list::sort` | allocation-free, **stable, bottom-up binned merge sort** (SGI/EASTL), O(log n) stack bins, relinks only | the whole point vs `Array::sort` is zero allocation + stable; `mSize` invariant under sort. |
| R32 | `fixed_list` / `fixed_slist` (Phase 5b) | **inline zero-heap node pool + free-list, hard-cap (R6)**; reuse the exported `List`/`ForwardList` node + iterator types (full iterator interop); MOVE/SWAP are **element-wise** (NOT pointer-steal); **no `splice`** (cross-pool node identity can't hold); `merge` is element-wise + capacity-checked; in-place `sort`/`reverse`/`remove`/`removeIf`/`unique` relink own nodes; NOT trivially relocatable | the EASTL fixed_list game staple: stable addresses + O(1) middle insert/erase with ZERO allocator traffic and nodes packed in the object's storage. Inline storage means node identity can't transfer between objects/pools — so move/swap copy elements and splice is omitted (physical constraint, not std-mimicry). Heap-spill overflow is a deferred opt-in (per R6). |

## Phase 6 — perf validation (bench-driven, 2026-06-01)
Goal: container perf **≥ STL, ≈ EASTL**. Benches (`bench/`, nanobench, release/NDEBUG) drove these.
| # | Decision | Choice | Why |
|---|---|---|---|
| R33 | Default allocate seam | `memory::allocate`/`deallocate` are **`inline`** + take the plain (non-aligned) `operator new` fast path when `alignment <= __STDCPP_DEFAULT_NEW_ALIGNMENT__` | bench showed `List` ~13% slower than `std::list` on push purely from the allocator: the non-inlined wrapper + `AllocInfo`/`source_location` plumbing couldn't be optimized out, and the aligned-new overload is a slow path on libc++. `inline` lets the optimizer strip the unused tracking to a bare `operator new`; the alignment check avoids posix_memalign for normally-aligned nodes. Result: `List<int,ThinAlloc>` == `std::list`, default `List` within noise. Reinstate an out-of-line def when the tracking allocator lands. |
| R34 | `List::sort` inner merge | sort over the **`mpNext` chain only** (1 pointer write/node), then rebuild `mpPrev` + re-circularize in one O(n) pass — instead of the SGI ring-splice (`transfer`, ~6 writes/node) | bench showed the ring-splice merge ~20-34% slower than `std::list::sort`. Halving inner-merge pointer traffic brought `List::sort` on par with `std::list::sort`. Stability + `mSize`-invariance unchanged. (`fixed_list` still uses the ring-splice sort; not hot, small N.) |
| R36 | `stableSort` (resolves R13) | **allocation-free in-place merge sort** (SGI rotation-based `__merge_without_buffer`: split larger run, binary-search the cut, `rotate`, recurse), small runs → stable insertion sort. O(n log² n) worst case | keeps the algorithm module allocator-free (R12) instead of the buffered O(n log n) that R13 deferred for needing scratch. Reuses `lowerBound`/`upperBound`/`rotate`. Buffered variant remains a future opt for hot stable sorts. |
| R39 | 3-way bench vs std + EASTL (release/NDEBUG, arm64, EASTL 3.27.1) | added EASTL to the bench feature; full worse/std/EASTL table. **We win:** hash INSERT (~1.5× std & EASTL), fixed_list/fixed_slist (zero-heap, 18-26×), FlatMap lookup (1.8× std::map / 1.9× eastl::map), forward_list sort vs eastl::slist (4×). **We match:** list/forward_list push & sort, introsort (~within 10% of std/EASTL), List::sort. **We LOSE (two real gaps → follow-ups):** (1) **hash LOOKUP ~2× slower than EASTL** (eastl::hash_map/set ~3.1k ns vs ours ~6.4-7.3k) — EASTL caches the hash code in the node so probe compares are cheap; ours recomputes/compares keys. Candidate: cache H1 or store hashes (R22 left "no cached hash in v1"). (2) **stableSort 3-12× slower** (worse ~190k vs std ~18k, eastl ~74k) — our alloc-free in-place merge is O(n log²n) by design (R36); std/EASTL use an O(n log n) temp buffer. Candidate: buffered stableSort. Also `Array<int>` push ~8× std/eastl::vector (vectorization, R35). | honest scoreboard: meets the ≥STL bar broadly and beats EASTL on insert/fixed/flat; two clear, well-understood optimization targets remain (hash-code caching, buffered stable sort). |
| R44 | **P7-introsort_tune** (Phase 7; last R39 gap — `sort` vs `std::sort`) | `worse::sort` trailed libc++ `std::sort` by a stable ~13% on random int (32.6k vs 28.9k) while **beating `eastl::sort`** (~33–43k, noisy). libc++'s edge is its modern sort (branchless partition + sort3/4/5 networks + pattern detection). **Added a branchless Lomuto partition** for trivially-copyable types (the pdqsort/Rust/libc++ lever): median-of-3 pivot moved out, every element unconditionally swapped with a BRANCHLESS `store += (x < pivot)`, pivot dropped into place; `introsortLoop` recurses both sides EXCLUDING the pivot (guarantees progress, no interior-sentinel assumption). Hoare kept for expensive-to-swap types (branchless over-swaps). **Measured: NO net change on Apple Silicon** (~32.6k) — confirmed branchless via asm (`csinc`), but this μarch's strong branch predictor neutralizes the x86 misprediction win and the 2× swaps offset it; insertion threshold 16 is already optimal (24/32/48 all worse). **Decision (user, 2026-06-02): KEEP branchless** — it's the standard cross-platform choice, neutral on the Apple-Silicon dev machine but a real win on the x86 consoles/PC the engine ships to; correct + stress-tested (heavy-duplicate ×200 sorts, organ-pipe). | last Phase 7 item closed honestly: the textbook lever was implemented and proven branchless + correct, but its benefit is x86-specific — Apple Silicon shows the same ~13% residual, which (like `std::stable_sort`, R41) is a libc++ expert-tuned outlier we can't cheaply match. We meet the real bar: beat EASTL, match std where the lever pays. |
| R43 | **P7-default_alloc_fastpath** (Phase 7; resolves R39's node-push default-allocator gap; refines R33) | Default-`Allocator` `List`/`ForwardList` push trailed `List<ThinAlloc>`/std by a *stable* ~9–11%. Asm (same diagnosis style as R42): the push loop called `Allocator::allocate(size, align, 0, source_location)` and the destructor called `Allocator::deallocate` **out-of-line** (`bl ...Allocator8allocate...`) — the compiler left them un-inlined, so the `AllocInfo`/`source_location` tracking was NOT DCE'd (it lives inside the opaque callee), the `operator new` `returns_nonnull` couldn't propagate (the null-check survived), and every node paid a call frame. `ThinAlloc` (inline `::operator new`) compiled the push to a bare `bl __Znwm`. R33 had inlined `memory::allocate` but `Allocator::allocate` itself stayed out-of-line. **Fix:** `WE_FORCEINLINE` on `Allocator::allocate` (both overloads) + `deallocate` → the tracking + null-check DCE to a bare operator new/delete, matching ThinAlloc. **Bench: List push ~70.7k→~65.2k (= std/ThinAlloc, was +9%); ForwardList push ~57.9k→~50.2k — now BEATS std::forward_list (51.4k) & eastl::slist (51.1k).** Sort-rebuild (alloc-free sort + build/free) now within noise. One-line-per-method change; the AllocInfo seam stays intact for when the tracking allocator lands (reinstate out-of-line defs then, per R33). | the same register-promotion/inlining lever as R42, applied to the allocator seam: an out-of-line `&this`/allocator call defeats DCE + costs a frame; force-inlining lets the dead tracking vanish. Confirms the [[container-push-register-promotion]] insight generalizes from container members to the allocator hot path. |
| R42 | **P7-array_trivial_push** (Phase 7; resolves the R35/R39 `Array<int>` push gap) | The `Array<int>` push-with-reserve microcase was ~5× slower than std/eastl::vector (~5.8k vs ~1.1k ns). **Root cause was NOT vectorization** (R35's hypothesis): LLVM `-Rpass-analysis=loop-vectorize` shows *neither* our loop *nor* std::vector's vectorizes — both are scalar. The real cause, found by reading the arm64 asm: std::vector keeps `__end_`/`__cap_`/counter in **registers** across the push loop (its grow/slow path is inlined, so the optimizer promotes the vector's members out of the object), while our `emplaceBack`'s grow path was reached as an **out-of-line `&this` call** — the optimizer then had to pin `mpBegin/mpEnd/mpCapacity` in the Array object's memory and **reload+spill them every iteration** (`ldp [sp,#40]` / `str [sp,#40]` per element). **Fix:** mark `emplaceBack`/`pushBack` `WE_FORCEINLINE` with the grow branch **inline** (`[[unlikely]]`), so no opaque `&this` call sits in the loop and the members promote to registers. **Bench: ~5.8k → ~1.13k ns, parity with std::vector (1.11k) / eastl::vector (1.11k)**; push-without-reserve 6.1k→1.7k too. Works for **all** element types (no trivial-only special-case, no AllocatorTraits-seam change). Tradeoff: the grow path is inlined at every push site (std::vector makes the same choice) — acceptable under the game-perf directive. Supersedes the deferred P6-array_vectorize / "trivial-store fast path" framing. | the obvious fix (a trivially-copyable direct-store fast path) was a red herring — measured no change across 4 variants (placement-new, outline, force-inline-tiny, assignment). Asm-level diagnosis found the true lever (register promotion blocked by an out-of-line grow call); the fix is one attribute, type-agnostic, and leaves the allocator seam untouched. |
| R41 | **P7-stable_sort_buffered** (Phase 7; resolves R39 gap #2, reopens R13/R36) | `stableSort` now takes a **runtime scratch buffer** (`std::stable_sort` shape): at runtime it grabs an `(n+1)/2`-element buffer from the default allocator (`worse.core.memory`) and runs a **buffer-the-left-half top-down stable merge** — move the left run into scratch, merge it back in place; the output cursor provably never overtakes the unconsumed right run, so only half the data is buffered. During **constant evaluation** OR if the allocation fails, it falls back to the **allocation-free in-place rotation merge** (R36) — so the algorithm module still works allocator-free where it must (constexpr/freestanding); only the hot runtime path allocates. `import worse.core.memory` + `#include <new>` added to `sort.cppm`. **Bench (4096 random int, arm64 release): 192–223k → ~72k ns/op (~3×), now BEATS `eastl::stable_sort` (~74k)**; `std::stable_sort` (libc++) stays ~17.7k. A trivially-copyable bottom-up **ping-pong** variant was prototyped and **measured no faster** (~75k, within noise) so was dropped — both plateau at ~72k and libc++'s 4× edge is a deeper constant even EASTL doesn't match. | un-defers R13's buffered O(n log n) (R36 kept it as a "future opt"); the user-set bar is "≥ STL OR ≥15% behind EASTL" → resolved: we now lead the realistic game-lib reference (EASTL). Kept the in-place merge as the constexpr/no-alloc fallback rather than deleting it, so no capability is lost. Honest note: libc++ remains ~4× ahead via an exceptional merge; chasing it past EASTL parity is diminishing returns (prototyped, no win). |
| R40 | **P7-hash_cache deferred** (Phase 7; bench-driven re-diagnosis of R39 gap #1) | An **identity-hash experiment** (temporarily `hashFinalize(x)=x`, release rebuild, re-measure, revert) proved R39's "EASTL caches the hash → cheap probe compares; ours recomputes/compares keys" diagnosis WRONG for our int-keyed bench: with a **free hash**, Robin Hood lookup did not move (UnorderedMap 7.3k→7.2k, UnorderedSet 6.3k→6.3k) while EASTL stays ~3.2k. Keys are `int`, so `KeyEqual` is a single compare — **caching a per-slot hash to skip key recompare cannot help here**; it only pays for EXPENSIVE key comparisons (`String`), and `Hash<String>` is not shipped (floats also deferred). We already **beat `std::unordered_set`** (6.3k vs 9.7k); the residual ~2× to EASTL is **structural** — EASTL's cache-warm, contiguously-allocated chained nodes pipeline better for in-L1 int lookups than open-addressing's 2-array scattered probe. **SwissTable IS partly hash-bound** (10.5k→7.1k w/ free hash) — its h2/pos extraction + SWAR amplify hash cost. **Decision (user, 2026-06-02):** defer `P7-hash_cache` until `String`/expensive keys land (when the architecture actually pays); pursue the clearly-winnable **P7-stable_sort_buffered** (~12× lever) next. | don't ship architecture against a mis-diagnosed bench number — measure the lever first. The hash-cache design is sound but premature without heavy keys; revisit alongside `Hash<String>`. Honest scoreboard unchanged: we meet/beat std on hash lookup; EASTL's int-lookup edge is a known structural property of chaining vs open addressing, not a fixable key-recompare cost. |
| R38 | SwissTable (Phase 6) | portable **SWAR control-byte** open-addressing engine (abseil flat_hash design): 1-byte control per slot (7-bit H2 / empty / deleted), 8-slot groups scanned branch-free via u64 SWAR, linear group probing, first-group control MIRROR for branchless wrap (no sentinel — iteration is index-bounded), 7/8 max load (R23), tombstones reclaimed on rehash. Same `<Value,Key,KeyOfValue,Hasher,KeyEqual,Allocator>` facade as `hash_table` (R8). Insert is single-probe (find-or-prepare in one pass). Stress-verified (8000 ops vs std::set). | the modern game-grade hash. **Bench (int keys): insert ~1.5× std, lookup ~1.3× std; our Robin Hood is still fastest for int** (SwissTable's H2 prefilter pays off more with expensive/string keys). Both engines beat std; SwissTable available behind the facade for a future default swap (esp. string keys). SWAR assumes little-endian. |
| R37 | Ordered associative (Phase 5c) | `rb_tree` engine (canonical SGI/libstdc++ insert/erase rebalance, embedded header sentinel, KeyOfValue extractor — mirrors `hash_table`) + thin `Set`/`Map` adapters. Move/swap re-seat the root's parent onto the new header (embedded-sentinel subtlety, cf. List). Verified by a 6000-op randomized stress test cross-checked vs `std::set` with full RB+BST invariant after every mutation (`checkInvariant`). | completes the container roster; un-defers R3. **Game-perf caveat in the headers**: rb-trees are the least cache-friendly ordered container — prefer `FlatSet`/`FlatMap` (cache) or `UnorderedSet`/`UnorderedMap` (hash); use `Set`/`Map` only for ordered iteration WITH stable refs + O(log n) mutation. |
| R35 | Bench results vs std (release/NDEBUG, this machine) | **node lists ≈ std** (List/ForwardList push + sort on par; `List<int,ThinAlloc>` == `std::list`); **hash beats std** (UnorderedMap insert ~1.5×, UnorderedSet insert ~1.9×, lookup ≈ on par); **FlatMap lookup ~1.8× std::map** (flat array vs rb-tree); **fixed_list/fixed_slist 17-24× std::list** (zero heap). **Open item:** `Array<int>` trivial push+reserve is ~4-7× slower than `std::vector` ONLY for trivially-copyable elements — libc++ vectorizes that loop; our `AllocatorTraits::construct` passes the allocator by ref so the optimizer can't prove non-aliasing and won't vectorize. Closes for realistic payloads (memory-bound). Tracked as a future allocator-seam optimization (e.g. a trivial-store fast path); container layout already matches std. | meets the goal (≥ STL, ≈/› EASTL) for the node + associative families; the one trivial-int contiguous microcase is a codegen artifact, documented not hidden. |

## Phase 8 — design audit & hardening (game-perf + predictability re-review, 2026-06-02)
| # | Decision | Choice | Why |
|---|---|---|---|
| R45 | **Full design audit vs the two locked principles** (game-performance-first + predictability) → opens **Phase 8** | Re-reviewed all **24 container + 6 algorithm** modules via 5 parallel specialist passes + **direct source verification of every load-bearing claim**. **Verdict: the architecture honors both principles** — centralized trivial relocation (memory_util.cppm:172-197), R42/R43 force-inline, flat-as-default, stable-address node containers, O(1)-size-across-splice correct in every overload (list.cppm:702-722), introsort O(n log n) guarantee (sort.cppm:327-332), rb_tree honestly self-positioned as the least cache-friendly ordered container (rb_tree.cppm:23-27). Gaps cluster in **two cross-cutting predictability themes, both release-build**: **(1) "enforced" preconditions are debug-only** — every hard-cap/overflow guard uses `WE_ASSERT`, which is `((void)0)` under `NDEBUG` (macro.hpp:57,63), so FixedArray/FixedList/FixedSList overflow + Array `kMaxElements` become **silent UB in shipping**, contradicting the docs' "hard-cap (no heap spill)" promise → **P8-hardcap_verify** (needs a fail-closed-vs-document sign-off; refines R4/R6/R22). **(2) OOM is throwing-new + a UB sink** — `memory::allocate` uses throwing `::operator new` (never returns null), so every container's `p==nullptr` / `handleAllocationFailure` path is dead code, and `handleAllocationFailure` itself is `unreachable()` = UB; `stableSort`'s documented alloc-fail in-place fallback (sort.cppm:397, R41) is therefore **unreachable** → **P8-oom_predictable** (pure win). Unrealized levers: `fill`/`fillN` lack the memset fast path copy/move already have (→ P8-fill_memset); the hash family uses `WE_FORCEINLINE` **0×** despite the R42/R43 precedent (→ measured P8-hash_forceinline); `PriorityQueue` has no `reserve` seam (→ P8-pq_reserve). Semantics/doc gaps: SwissTable tombstone→same-capacity rehash is a surprise mid-frame stall and `reserve` doesn't reclaim tombstones — the Robin Hood engine is tombstone-free by construction (→ P8-swiss_tombstone); ordered Set/Map lack the transparent lookup flat_* has (→ P8-ordered_transparent); Map double-descends the tree on insert-or-update (→ P8-map_single_descent); misc erase-range-assert / equal-priority-determinism / SWO-contract docs (→ P8-polish). **One alleged correctness BLOCKER DISPROVED:** the Robin Hood duplicate-insert claim (hash_table.cppm:586) was investigated and is **correct code** — the dup guard `info==dist && keyEqual` mirrors `findIndex` (:554) and the RH invariant guarantees the existing key is reached *before* any `info<dist` steal, so the guard stays armed until it fires; the reviewer's scenario (a steal with no `info<dist` slot) is internally inconsistent. | don't ship hardening against unverified claims — the dup-insert "bug" was a specialist-review false positive caught only by reading the invariant, so every load-bearing claim was source-verified before landing as a task. And don't let the predictability principle be a *debug-only* promise: both themes are exactly where "bounded, fail-closed, deterministic" silently degrades to UB in the shipping build that ships to consoles/PC. ## Non-negotiable conventions (from the existing tree)
- C++20 modules, one `.cppm` per unit, module name mirrors path.
- camelCase methods, PascalCase types, `m`/`mp` members, `k`/PascalCase static constants, `WE_*` macros.
- All allocation + element lifetime via `AllocatorTraits<Allocator>`; byte-based allocator (not templated on T); `WE_NO_UNIQUE_ADDRESS` EBO.
- No exceptions: `WE_ASSERT`/`WE_VERIFY` + abort + sentinel returns.
- Base/Derived split for heap-owning containers (storage+RAII in `XBase`, API in `X`).
- Math `min/max/clamp/abs` already exist — reuse, never duplicate.
- **In-house trait vocabulary only**: use the `worse::core` `IsXxx`/`RemoveXxx` wrappers from
  `type_traits.cppm`, not raw `std::` trait queries, in module code. Add a wrapper when one is
  missing rather than reaching for `std::`. (Pure metaprogramming primitives with no wrapper —
  `void_t`, `true_type`/`false_type`, `bool_constant` — may stay `std::`.)
- **No `*_detail` sub-namespaces**: internal helpers go in the module's MAIN namespace
  (e.g. `worse::core`), simply left out of the `export` block. Module linkage already hides
  non-exported names from importers with no cross-module clashes (see `allocator_traits.cppm`,
  `heap.cppm`, `sort.cppm`).
