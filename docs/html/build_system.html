Build System

The build is organized so that decisions (what to build, with which options) live at the root, capabilities (reusable flags, defines, helper functions) live under cmake/, and each library only declares what it is and what it depends on. Adding a subsystem is one worse_add_library() block plus a one-line dependency edge — not edits scattered across a monolithic script.

Repository layout

CMakeLists.txt # thin entry: project() + global C++ settings, then include + add_subdirectory
cmake/
WorseOptions.cmake # every option() in one place
WorsePlatform.cmake # host platform/arch -> WE_* preprocessor defines
WorseCompileOptions.cmake # worse::build_options (PUBLIC) and worse::warnings (PRIVATE)
WorseHelpers.cmake # worse_add_library / worse_add_test / worse_add_bench
WorseDocs.cmake # the Doxygen `docs` target
src/worse/
CMakeLists.txt # `worse` facade target (aggregates the enabled subsystems)
core/CMakeLists.txt # worse::core subsystem library
tests/{,core/}CMakeLists.txt # one test executable per sub-area
bench/{,core/}CMakeLists.txt # the bench_core binary

The root CMakeLists.txt does nothing but project(), a handful of global settings, and include() of the four capability modules in order (options → platform → compile options → helpers), then add_subdirectory() for src/worse, tests, and bench.

Presets

All builds go through CMakePresets.json, which wires the vcpkg toolchain from $VCPKG_ROOT and the Ninja generator. Output lands in build/<preset>/.

Preset Build type Adds
debug Debug assertions on (default day-to-day)
release Release optimized, NDEBUG
relwithdebinfo RelWithDebInfo optimized + line info
asan RelWithDebInfo ASan + UBSan, assertions forced on (see Sanitizers, LTO, and assertions)
lto Release ThinLTO / IPO
cmake --preset debug # configure
cmake --build build/debug # build everything (libs + tests)
ctest --preset debug # run the full suite
ctest --preset debug -R '^core_math\.' # run just one sub-area (see bs_tests)
ctest --preset asan # full suite under AddressSanitizer

Options

Set with -DWORSE_…=ON at configure time, or bake into a preset's cacheVariables.

Option Default Effect
WORSE_BUILD_TESTS ON when top-level build the unit tests
WORSE_BUILD_BENCH OFF build the benchmarks (needs the vcpkg bench feature)
WORSE_BUILD_DOCS OFF expose the Doxygen docs target
WORSE_BUILD_SHARED OFF build the engine libraries as shared instead of static
WORSE_BUILD_CORE ON build the core subsystem
WORSE_BUILD_TESTS_CORE ON build the core tests
WORSE_BUILD_BENCH_CORE ON build the core benches
WORSE_ENABLE_WERROR OFF warnings as errors
WORSE_ENABLE_LTO OFF IPO/LTO for the optimized configs
WORSE_ENABLE_SANITIZERS OFF ASan + UBSan
WORSE_ENABLE_ASSERTS OFF force WE_ASSERT on even in NDEBUG builds
WORSE_FORCE_SCALAR_SIMD OFF disable SSE/NEON, use the scalar SIMD fallback

Naming convention

One rule disambiguates the two namespaces of identifiers:

  • WORSE_* — build-system identifiers: CMake variables, option()s, the worse_* target prefix.
  • WE_* — C++ preprocessor symbols visible to code: macros and #if defined switches.

The build injects this set of WE_* symbols (carried PUBLICly by worse::build_options, so they reach every TU — macros do not propagate through import):

Symbol Source
WE_PLATFORM_WINDOWS / _MACOS / _LINUX CMAKE_SYSTEM_NAME
WE_ARCH_AMD64 / WE_ARCH_AARCH64 CMAKE_SYSTEM_PROCESSOR
WE_BUILD_DEBUG / WE_BUILD_RELEASE the build config
WE_VERSION_MAJOR / _MINOR / _PATCH project(VERSION)
WE_ENABLE_ASSERTS WORSE_ENABLE_ASSERTS
WE_SIMD_FORCE_SCALAR WORSE_FORCE_SCALAR_SIMD

Libraries, compile options, and dependencies

Every engine library is created through worse_add_library(<subsystem> …), which produces a worse_<subsystem> target plus a worse::<subsystem> alias and, by default, links two interface carriers:

  • worse::build_options (PUBLIC) — propagating: the C++ standard level, the WE_* defines above, and sanitizer/LTO flags. PUBLIC so consumers inherit the same defines.
  • worse::warnings (PRIVATE) — non-propagating: /W4 /permissive- (MSVC) or -Wall -Wextra -Wpedantic (Clang/GCC), plus -Werror when WORSE_ENABLE_WERROR.

Dependencies between subsystems are declared as edges, not implied by directory order:

worse_add_library(core
MODULES ${CORE_MODULES} # C++20 interface units, listed explicitly (the BMI graph)
HEADERS ${CORE_HEADERS} # textual headers, globbed
SOURCES ${CORE_SOURCES}) # implementation TUs, globbed
# core is the base — no PUBLIC_DEPS

Module interface units (.cppm) are listed explicitly because they define the public module graph and the BMI build order, so additions should be intentional and reviewable; .cpp/.hpp are globbed per directory with CONFIGURE_DEPENDS. A subsystem's modules are PUBLIC in a FILE_SET CXX_MODULES, so any target that links it can import them (CMake ≥ 3.28).

Note
Library granularity is one subsystem per directory under src/worse/. core is a single library; container/algorithm/math/coroutine are module partitions inside it (container and algorithm are mutually dependent via iterator/sort, so they cannot be separate targets). Future subsystems — e.g. RHI, render — are sibling libraries.

Adding a subsystem

To add, say, an RHI library that builds on core:

1. Declare the library in src/worse/RHI/CMakeLists.txt:

worse_add_library(rhi
MODULES rhi.cppm device.cppm swapchain.cppm
PUBLIC_DEPS worse::core) # the dependency edge — one line

2. Wire it in from src/worse/CMakeLists.txt — gate it, then aggregate into the facade:

if(WORSE_BUILD_RHI)
add_subdirectory(RHI)
endif()
if(TARGET worse::rhi)
target_link_libraries(worse PUBLIC worse::rhi)
endif()

3. Register the options WORSE_BUILD_RHI (and optional WORSE_BUILD_TESTS_RHI / _BENCH_RHI) in cmake/WorseOptions.cmake, and mirror the directory under tests/ and bench/.

Per-library symbols or flags beyond the shared carriers go on the same call via the DEFINES (PUBLIC) and OPTIONS (PRIVATE) arguments of worse_add_library.

Tests and benchmarks

Tests are split per sub-area into independent executables — test_core_container, test_core_algorithm, test_core_math, test_core — via worse_add_test(). Editing one suite only relinks that executable, and each registers with a ctest prefix so groups select cleanly:

cmake --build build/debug --target test_core_math # build just the math suite
ctest --preset debug -R '^core_container\.' # run just the container group

Benchmarks are intentionally a single bench_core binary (not split): bench_main.cpp drives every suite against one shared nanobench::Bench so the relative-speed column compares across the whole run, and it is the sole owner of the nanobench implementation and EASTL's allocator hooks. Benches build -O2 -DNDEBUG so the template-heavy engine code is optimized and WE_ASSERT bounds checks compile out. nanobench + EASTL come from the vcpkg bench manifest feature:

cmake --preset release -DWORSE_BUILD_BENCH=ON -DVCPKG_MANIFEST_FEATURES=bench
cmake --build build/release --target bench_core
./build/release/bench/core/bench_core

Sanitizers, LTO, and assertions

WORSE_ENABLE_SANITIZERS adds matching ASan + UBSan compile and link flags; WORSE_ENABLE_LTO enables ThinLTO/IPO for the optimized configs after probing support.

Warning
The asan preset is RelWithDebInfo, not Debug, on purpose: on Windows the clang AddressSanitizer is incompatible with the debug CRT (/MDd → spurious bad-free inside ucrtbased). RelWithDebInfo keeps the release CRT (/MD) plus line info. On Windows the ASan runtime is a DLL with no static variant, so the build stages clang_rt.asan_dynamic-x86_64.dll next to each executable — otherwise it dies at startup with 0xc0000135 (including during gtest's build-time test discovery).

Assertions are decoupled from the build type: WE_ASSERT / WE_ASSERT_MSG are active unless NDEBUG is defined and WE_ENABLE_ASSERTS is not, so WORSE_ENABLE_ASSERTS=ON keeps them live in optimized builds (the asan preset turns this on). WE_VERIFY is always on regardless.
