Containers Guide

The library ships four container families. Choose by memory model first (where do the elements live, and do they move?) and access pattern second (indexed? keyed? ordered? FIFO/priority?). Each family page below has a per-type section: purpose, memory model, complexity, iterator/stability contract, when-to-use / when-to-avoid, key R## decisions, and an example.

Choosing a container

Complexities are amortized/average where marked; n = element count. "Stable iterators" means references/pointers/iterators to existing elements survive the listed mutations.

Rules of thumb

  • Default to Array. Contiguous wins on real hardware until measurement says otherwise. Reserve up front to make pushBack realloc-free.
  • Need stable references across edits? Use a node list (List/ForwardList), or an IntrusiveList when the objects already live elsewhere.
  • Per-frame, bounded, zero-allocation? FixedArray / FixedList / FixedSList — they never touch the heap and fail closed at capacity (with try* escape hatches).
  • Keyed lookup, don't care about order? UnorderedMap/UnorderedSet. Read-mostly small/medium sets are often faster in a FlatSet/FlatMap.
  • Need sorted iteration or range queries (lowerBound/upperBound)? Set/Map for churn with stable iterators, FlatSet/FlatMap for read-mostly cache-friendliness.
